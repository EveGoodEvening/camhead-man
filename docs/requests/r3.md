# r3：R3 区域代理的需求与缺陷

> 唯一写入者：R3 区域代理（ARCH §2.12、§15.6）。只追加；引擎维护者的结论写在 `docs/requests/m2-engine.md`。

## 1. 带 castShadow 的灯在第二次进入区域时刷 GL_INVALID_OPERATION（sampler 与贴图格式不符）
- 类型：引擎缺陷
- 现象/需要什么：GDD §9.3/ARCH §13.1 给 R3 影棚的钨丝灯留了全局唯一的投影光（512 阴影贴图）。R3 用 `lamp({ kind:'tungsten_pendant', light:{ design:1.6, distance:6.5, castShadow:true } })` + `ctx.light()` 登记。**第一次**进 R3 一切正常；**再进一次**（`shot('r3', …)` 连拍两张、`setState({area:'r3'})`、走出去再走回来都一样）就刷
  `GL_INVALID_OPERATION: glDrawElements: Mismatch between texture format and sampler type (signed/unsigned/float/shadow).`（Chrome 很快报 “too many errors”），harness 判失败。
  复现：`quality=high`（low 档关阴影不复现），`__game.shot('r3','shot.r3.hall')` 连调两次；把 castShadow 改成 false 立刻不复现；只保留灯的 castShadow、所有网格都不 castShadow/receiveShadow 仍然复现——跟灯本身/阴影贴图的生命周期有关（猜测：区域卸载时 Disposer 释放了旧灯的 `shadow.map`，新区域预编译/预热在 `shadowMap.needsUpdate` 之前渲染，某个纹理单元还绑着旧的深度纹理，或 `emptyShadowTexture` 的比较模式没对上）。
- 影响：R3 影棚没有投影（观感：影棚里大件没有影子，钨丝灯的光会稍微漏过影棚北墙照进暗房南半边）。不影响 §11 任何步骤。
- 临时绕开：`src/areas/r3/build/studio.ts` 的 `STUDIO_SHADOW = false`（钨丝灯退成点光）。引擎修好后改回 `true` 即可（影棚大件、北墙、暗房门都已经写了 castShadow/receiveShadow）。
- 状态：resolved（M3）：根因——`shadowMap.autoUpdate = false` 时新灯的 `shadow.map` 要等第一次阴影 pass 才建，进区域的预编译/预热先渲染了；r186 给 `sampler2DShadow` 数组绑的空深度贴图（`WebGLUniforms` 的数组 setter 不设 `emptyShadowTexture.compareFunction`）没有比较模式。修法：`core/area.ts` 在 `precompile`/`warmupArea` 之前就 `renderer.shadowMap.needsUpdate = true`（预热顺带建好阴影图）。实测：build 里直接开投影、`shot('r3')` 连进三次，修前第 2、3 次各 257 条 GL_INVALID_OPERATION，修后 0 条。R3 改回 build 里 `castShadow = true`（`STUDIO_SHADOW = 'build'`，`r3/build/studio.ts`），`enterLogic` 不再开投影。ARCH §4.5。

## 2. GameApi 没有“打开墙上/场景里文档”的入口（doc.darkroom_rules）
- 类型：接口需求
- 现象/需要什么：GDD §13.9 的 `doc.darkroom_rules` 贴在暗房门背后（交互物 `r3.darkroom_rules`），不属于任何物品。`JournalSystem.openDoc(id)` 能打开任意已登记的文档，但区域代码只能拿到 `GameApi`，上面没有 `openDoc`，Effect 里也没有 `{ do:'doc' }`。请在 `GameApi` 加 `openDoc(id: DocId): ApiResult`（或 Effect `E.doc(id)`），行为同物品栏点开文档（`vf` 缺省 = 栈上有取景器）。R1 的公告栏（讣告、拆迁公告、停水通知）、小区简介牌、监控调试注意事项应该也是同样的需求。
- 影响：GDD P7 线索“暗房守则（全文见第 7 节）”。不阻塞 §11 步骤（步骤 34 不读守则）。
- 临时绕开：`r3.darkroom_rules` 的 onInteract 开旁白对话 `dlg.r3.rules`，把守则全文逐条念出来（文字与 `doc.darkroom_rules` 同源，都在 `src/areas/r3/text.ts`）；门背后的守则纸本身是 `ctx.hdText` 贴图，取景器 ≥2× 能直接读清。引擎加了入口后改成 `g.openDoc(DOC.DARKROOM_RULES)`。
- 状态：resolved（M3）：`GameApi.openDoc(id, o?)`/`openJournal()` 与 Effect `E.doc(id, vf?)`/`E.journal()`（`game/effects.ts`；阻塞到阅读器合上，连写几个就是一张接一张读；阅读器开着时 settle 为 'waiting'），`DebugState.doc`（`debug/api.ts`），测试助手 `readDocs`（`scripts/lib/harness.mjs`）；ARCH §6.3、§6.16、§12.3。R3 已换回阅读器：`r3.darkroom_rules` 的 `onInteract: [E.doc(DOC.DARKROOM_RULES)]`（`r3/logic.ts`），`dlg.r3.rules` 删除；`regions/r3.mjs` 用 `readDocs` 断言。

## 3. lint 的“暗房容器”组要求三件容器角标文字相同，与 GDD §10.2 冲突
- 类型：引擎缺陷（文档矛盾）
- 现象/需要什么：`src/debug/fidelity.ts` 的 `LINT_GROUPS` 把 `r3.tray_square` `r3.basin_xi` `r3.plate_chipped` 编成一组，签名里比较 `stripOrdinals(label)`；而 GDD §10.2 与 ARCH §6.6 硬规则要求三件容器“只按形状叫‘方盘’‘深盆’‘豁口盘’”——三个角标文字本来就不同，所以只要三件容器在场，`lint()` 就报
  `r3: 同组“暗房容器”不一致：r3.tray_square ["white","方盘",…] ≠ r3.basin_xi ["white","深盆",…]`，`check.mjs` 因此算违规。
  建议：这一组只比较灰/白、hasOffers、是否弹动作菜单、menuVerb（不比文字），或者对这一组把文字比较换成“不含颜色字（黄/红/白）”。
- 影响：`node scripts/check.mjs` 的 lint 项（R3 完成定义第 1、4 条）。R3 的实现按 GDD：三件容器同一可用性、都没有 offers、都只有主动作，色彩辅助只走 `colorHint` 且红灯下现算为 `undefined`。
- 临时绕开：无（不能为了过 lint 把角标改成同一个字，那样违背 GDD）。当前 check.mjs 进 r3 时容器 present 为假（人在出生点、不在暗房里，见 #5 的就近聚焦绕开），这一条暂时不会冒出来；人在暗房里调 `lint()` 会冒出来，`scripts/regions/r3.mjs` 过滤了这一条。
- 状态：resolved（M3）：`debug/fidelity.ts` 的 `LINT_GROUPS` 加 `label: 'shape'`，“暗房容器”组只比较灰/白、hasOffers、动作菜单、menuVerb，另查角标里不许有颜色字（红黄白绿…）；`regions/r3.mjs` 去掉对这一条的过滤。

## 4. 截图机位没法设区域临时状态（暗房红灯），且单红通道画面亮度到不了 0.8
- 类型：接口需求
- 现象/需要什么：暗房红灯是区域临时状态 `safelight`（GDD §3.13“暗房步骤属于临时状态”），`ShotDef.preset` 只能设 flags/物品/照片，所以 `shots.mjs` 拍不到红灯画面；另外红灯时 `CameraFxPass` 把画面压成 `(v, 0.06v, 0.05v)`，亮度上限约 0.26，`shots.mjs` 的“亮度 > 0.8 的像素 ≥ 0.5%”对这类画面永远不成立。请给 `ShotDef` 加 `temp?: Record<string, boolean | number>`（进区域后 `ctx.setTemp`），并允许机位声明 `highlight: false` 跳过高光验收（或按单红通道换算阈值）。
- 影响：R3 截图验收；不影响玩法。
- 临时绕开：`scripts/regions/r3.mjs` 在真实流程里拉灯绳后截图到 `test-artifacts/r3/darkroom_red.png`，并断言画面 G/B 通道几乎为零（单红通道生效）。
- 状态：resolved（M3）：`ShotDef.temp`（同 r2.md #2）与 `ShotDef.highlight`（高光阈值，默认 0.8，`false` 不验；`scripts/shots.mjs` 按它统计）；R3 在 `safelight` 被别处写进临时状态时也换灯（`r3/logic.ts` 监听 'temp'），新增取景器机位 `shot.r3.darkroom_red`（`temp: { safelight: true }`；红灯泡在头顶正上方框不进画，单红通道里没有高光，故 `highlight: false`、`brightness: [0.01, 0.3]`，单红通道本身仍由 `regions/r3.mjs` 的真实流程断言 G/B ≈ 0）。ARCH §12.5。

## 5. 就近聚焦（聚焦规则 2）不看墙：隔着墙也会选中另一个房间的交互物
- 类型：引擎缺陷
- 现象/需要什么：`InteractionSystem.computeFocus` 的规则 2（射程内、身体前方 ±60° 取 priority 最高再取最近）不做遮挡检查。R3 影棚与暗房隔一道墙：站在坐凳前（GDD §11 步骤 37 的 `goto(r3,0,-9.0)`）、第三人称俯仰钳在 -35° 时中心射线打不到坐凳，规则 2 选中了 2.4m 外、墙那边暗房里的灯绳，`interact(r3.stool)` 返回 `not_focusable`。建议规则 2 对候选做一次 `occludesView` 射线（眼 → 锚点，止于锚点前 0.15m），被挡的不参与。
- 影响：步骤 37（已绕开）。
- 临时绕开：暗房里的交互物（灯绳、三件容器、水池、晾片绳、门背后的守则）`present` 现算“人在暗房里”（`src/areas/r3/logic.ts` 的 `IN_DARK`）。
- 状态：resolved（M3）：`game/interaction.ts` 的聚焦规则 2 对候选做与调试 API 真人路径检查同一判据的墙体遮挡测试（`collision.raycast(眼→锚点, 距离 − 0.15, { skipSeeThrough, ignoreKeys:[id] })`），隔着墙的不算；R3 的 `present: IN_DARK` 绕开已去掉（`r3/logic.ts`），步骤 37 照常通过。ARCH §6.6。

## 6. shots.mjs 的截图超时写死 30 秒，并行跑测试时偶发 TimeoutError
- 类型：引擎缺陷（测试工具）
- 现象/需要什么：`scripts/shots.mjs` 第 66 行 `h.page.screenshot({ path: file })` 用 Playwright 默认 30 秒超时；五个区域代理同时跑测试（load average 25+）时 1280×720 high 画质的 SwiftShader 截图会超过 30 秒，整个脚本抛 TimeoutError 退出。请给截图传 `timeout: 180000`（harness 的 `screenshot()` 同理）。
- 影响：`node scripts/shots.mjs --area r3` 偶发失败（与区域内容无关）。
- 临时绕开：负载低时重跑。
- 状态：resolved（M3）：同 r2.md #4（`scripts/shots.mjs` 超时可配、单张出错不中断、perf 按区域分文件）。

## 7. 调试 API 的 interact()：刚对一个方向差很多的目标交互过，紧接着 interact 另一个目标偶发 not_focusable
- 类型：引擎缺陷（测试工具，`src/debug/api.ts` 的 `prepare()` → `checkInteractFidelity`）
- 现象/需要什么：暗房里 `goto(r3,-1.5,-12.9)` → `interact(r3.lamp_cord)`（灯绳在东北上方）→ 立刻 `interact(r3.plate_chipped)`（豁口盘在西南下方，1.3m）稳定返回
  `{ ok:false, reason:'not_focusable', result:{ focused:'r3.tray_square' } }`；state：`yaw 291.79, pitch -30.4`（没钳制）。失败的那次 interact 已经把人转向了豁口盘；隔几帧（例如插一句 `goto(r3,-1.5,-12.9)`）再 `interact(r3.plate_chipped)` 就成功；拉完灯绳直接 `goto` 再 interact 仍然失败（`goto` 不改朝向）。
  推测：`turnTowards()` 之后 `cameras.sync()` 只同步了朝向，第三人称相机吊杆的碰撞收缩距离还是上一次朝向（灯绳那边、贴着东墙）的值，中心射线从墙里/墙外出发先打到墙，落回“就近聚焦”选了更近的方盘。建议 `prepare()` 在做真人路径检查前让第三人称吊杆的碰撞距离也立即收敛（或先跑一帧相机更新）。
- 影响：`scripts/regions/r3.mjs` 的用例“白灯下放胶卷 / 次序错……”（已绕开）；不影响 §11 步骤（步骤 34 的次序是方盘→深盆→豁口盘，转身角度小）。
- 临时绕开：用例里拉完灯绳先 `aimAt(r3.plate_chipped)` + `wait(0.5)`（让相机跟过来）再点豁口盘。（单插一句 `goto` 不够：`goto` 不改朝向；诊断里之所以“goto 之后就好了”，是因为前一次失败的 interact 已经把人转过去了。）
- 状态：resolved（M3）：根因不是相机吊杆没收敛（`cameras.sync()` 本来就 snap），而是 `PlayerController.lookAtPoint('tp')` 固定只迭代 3 次：第三人称相机偏在右肩、吊臂在小屋里随朝向时长时短，从差 150° 的朝向转过来收不拢，中心射线落到旁边的方盘上。改为迭代到收敛（≤ 12 次，变化 < 0.01°，`core/player.ts`）；复现脚本修前 `not_focusable {focused: r3.tray_square}`、修后直接成功。`regions/r3.mjs` 去掉 `aimAt + wait(0.5)` 的绕开。ARCH §4.9。

## 1 补记（R3 区域代理，2026-09-28）
- #1 的绕开方式已换成 `STUDIO_SHADOW = 'enter'`（`src/areas/r3/build/studio.ts`）：影棚钨丝灯是聚光灯，`build` 时不投影，`onEnter`（预编译、预热之后）再打开 `castShadow`。`shots.mjs --area r3`（quality=high，每个机位都重进一次 R3）不再刷 `GL_INVALID_OPERATION`。引擎修好后改成 build 里直接 `castShadow = true` 即可。

## Lessons
- 共用的 scratchpad 是所有并行代理同一个目录：自己的脚本、日志、截图一律放进私有子目录（R3 用 `scratchpad/r3w/`）并起不撞名的文件名——别的代理重写过同名的 `myshots.mjs`。
- 高负载（load 30+）下 SwiftShader 一个区域用例要 1–2 分钟：`regions/<id>.mjs` 放在**拷贝出来的** dist 上跑（`cp -r r3-dist r3w/dist-reg`），这样边跑测试边 `vite build --outDir r3-dist --emptyOutDir` 调截图不会把正在服务的构建删掉；`newGame()` 偶发 timeout 是负载问题，单独 `--case=` 重跑。`shots.mjs` 的截图 30 秒超时同理（#6），调图时用私有拷贝把 `page.screenshot` 的 timeout 放到 300 秒，最终再跑一遍正式脚本。
- 调试 API 的 `interact()` 在刚对另一个方向差很多的目标交互过之后可能 `not_focusable`（第三人称相机没跟上，#7）：用例里先 `aimAt(<交互物 id>)` + `wait(0.5)` 再 `interact`。`goto()` 不改朝向，解决不了。
- 区域拿不到相机（`GameApi`/`AreaContext` 都没有）：`skyDome()` 的网格 `frustumCulled = false`，在它的 `onBeforeRender(_r, _s, cam)` 里 `cam.getWorldPosition(v)` 就能拿到本帧镜头位置（自由机位、过场、回放都对），R3 用它让半球光在镜头进了照相馆时换成钨丝暖色（灯数不变，只改颜色与强度）。
- 取景器里“透光的正片/幻灯片”：`MeshStandardMaterial({ color: '#000', emissiveMap: 同图, emissive: '#fff', emissiveIntensity: 0.8–0.95 })`，不吃场景灯——挂在灯下的底片不会被“自发光 + 直射光”叠成一团白。
- 要读得清的灯箱（竖灯箱、横灯箱）：白底深色字，emissiveIntensity 0.7–0.9（白底刚好烧白、字还在）；到 1.0 以上 Bloom 把字糊掉。高光不够时再加亮窗/灯罩内壁发光，不要硬拉灯箱。
- 红灯单红通道的截图验收只统计画面上半部（y 12%–60%）并先 `wait(3)`：下半部的教学提示条、反馈条、字幕是 DOM，G/B 不为零，会把“非红像素”顶过阈值。
